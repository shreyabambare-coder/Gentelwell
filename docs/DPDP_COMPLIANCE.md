# Data Privacy, Regulatory Compliance & DPDP Dossier

**Regulatory Framework:** Digital Personal Data Protection (DPDP) Act 2023 (Government of India)  
**International Equivalencies:** GDPR (Articles 6 & 9 Special Category Data), HIPAA Security Rule  
**System Scope:** Gentelwell / Setu Health Platform  

---

## 1. Regulatory Context & Legal Baseline

Gentelwell processes health information for patients in rural Maharashtra (India). Under India's **Digital Personal Data Protection (DPDP) Act 2023** and the Information Technology (Reasonable Security Practices and Procedures and Sensitive Personal Data or Information) Rules, digital health platforms are classified as **Data Fiduciaries** handling sensitive personal data.

To ensure future-proof scalability, Gentelwell adopts an **architectural security posture aligned with international standards (HIPAA / GDPR)** so that deployments outside India require zero re-architecting of the data model.

---

## 2. Explicit, Versioned Consent Architecture

### 2.1 Consent Life-Cycle
In accordance with Section 6 of the DPDP Act 2023:
1. **Notice & Plain Language:** Consent notices are presented in the user's chosen language (Hindi / English) using visual icons and voice narration.
2. **Itemized Purposes:** Consent is not bundled. It is granularly partitioned into specific operational purposes:
   - `triage`: Running algorithmic symptom evaluations.
   - `care-coordination`: Sharing vitals and visit records with designated CHWs and clinicians.
   - `emergency`: Overriding access restrictions during life-threatening acute red flags.
   - `offline-sync`: Caching data on local hardware for rural offline continuity.
3. **Version Tracking:** The active consent schema is versioned (e.g., `v1.2-DPDP-2023`) and linked directly to the patient's FHIR `Consent` resource.
4. **Unconditional Withdrawal:** Patients can revoke consent at any time via `/api/v1/consent`, triggering automatic decommissioning of active sync routines.

## 3. API-Layer Purpose-of-Use Verification

Unlike naive architectures that check consent only on the client user interface, Gentelwell enforces purpose verification at the **server network boundary**:

```
+-------------------------------------------------------------------------+
|                  Client Request (PWA or Background Sync)                |
|  POST /api/v1/patients  HTTP/1.1                                        |
|  Host: localhost:3000                                                   |
|  purpose-of-use: care-coordination       <-- Validated by apiHelper.js  |
|  idempotency-key: idem_m7a92_b84z        <-- Deduplication Guard        |
+------------------------------------+------------------------------------+
                                     |
                                     v
                 +---------------------------------------+
                 | Is purpose-of-use present and valid?  |
                 +-------------------+-------------------+
                                     |
                +--------------------+--------------------+
                | No                                      | Yes
                v                                         v
   +---------------------------+             +---------------------------+
   | HTTP 403 Forbidden        |             | Process Mutation &        |
   | SECURITY_CONSENT_VIOLATION|             | Log Immutable Audit Trail |
   +---------------------------+             +---------------------------+
```

Every endpoint in `/api/v1/...` executes `checkPurposeOfUse()` before parsing the request payload. Unauthorized access attempts return HTTP `403 Forbidden`.

## 5. Software as a Medical Device (SaMD) Exemption Dossier

Under the Central Drugs Standard Control Organisation (CDSCO - India), US FDA, and EU MDR guidelines:
- If software claims to **diagnose, cure, mitigate, or treat** a disease, it is classified as a regulated **Medical Device (SaMD)**.
- **Gentelwell's Regulatory Safeguard:**
  1. The platform is explicitly positioned and labeled as an **Educational & Clinical Triage Decision-Support Tool**.
  2. All diagnostic language is forbidden in UI copy and model prompts (uses "Symptoms are consistent with...", never "You have Lipoma").
  3. Pre-assessment informed consent modals require users to acknowledge the non-diagnostic scope before accessing triage assessments.
  4. All high-risk cases require mandatory in-person physician palpation and soft-tissue ultrasound/MRI.

## 6. Data Localization & Encryption Checklist

| Security Control | Implementation |
| :--- | :--- |
| **In-Transit Encryption** | TLS 1.3 mandated across all external and internal API calls. |
| **At-Rest Encryption** | Local client stores use browser-sandboxed local storage; backend stores utilize AES-256 volume encryption. |
| **Data Residency** | All backend databases, Redis queues, and object stores reside strictly within Indian data centers (Mumbai/Pune cloud regions). |
| **Data Minimization** | No Aadhaar numbers, biometric fingerprints, or unnecessary personal identifiers are stored; only clinical vitals, ABHA IDs, and operational numbers are processed. |
